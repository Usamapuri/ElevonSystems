## What Phase 1 delivered

- **Login throttle**: `internal/ratelimit`, a sliding-window limiter with a bounded sweep (10 000 keys). Login enforces 10 failures / 15 min per identifier+IP → `429 rate_limited`.
- **Forgot / reset / change password**: `internal/email` wraps Resend (dev mode — `RESEND_API_KEY`/`EMAIL_FROM` unset — logs the reset URL instead of sending). `POST /auth/forgot-password` and `POST /auth/reset-password` are public; `POST /auth/change-password` is staff-only. Password policy is 8–72 bytes everywhere (`weak_password` / `password_too_long`). New env var `APP_URL` builds the reset link. `change-password` answers `400` (not `401`) for a wrong current password, so the client's global 401 interceptor doesn't log the user out.
- **`internal/staffpin`**: admin-only PIN identify, bcrypt-compares every candidate (no username-style lookup, so timing doesn't leak which PIN matched).
- **Users API**: `GET/POST /admin/users`, `PUT /admin/users/:id`, `PUT /admin/users/:id/pin`. Guard codes: `cannot_modify_self`, `last_admin`, `username_taken`, `email_taken`, `pin_in_use`, `pin_not_allowed_for_role`, `invalid_pin_format`. A Postgres advisory lock (`pg_advisory_xact_lock`) serialises PIN writes and role/active changes. Usernames are immutable; users are deactivated, never deleted; demotion clears the PIN.
- **Settings API**: `internal/settings` (21 keys, per-key rules, a `notNull` guard so only `tax_rate_credit` may be null, cross-key printable-width check, `Save` casts `$2::jsonb`). `GET /settings` (staff), `PUT /admin/settings` (admin, all-or-nothing) with codes `unknown_setting` / `invalid_setting_value`. `settings.LoadDayBoundaryHour` runs at boot and again after every save.
- **Settings screen**: tabs for Business, Tax, Receipt, Day close, Credit, and a Users tab (create, edit, deactivate, set-PIN dialogs).
- **Frontend auth surface**: `/forgot-password`, `/reset-password` pages, a login-page link to them, and a `ChangePasswordDialog` in the user menu.
- **Contract tests added**: `handlers/no_raw_error_contract_test.go` (no `err.Error()` reaches a client); the public-route contract test now pins the exact three public lines (`POST /auth/login`, `POST /auth/forgot-password`, `POST /auth/reset-password`).

## Deviations and gotchas to carry forward

From Phase 0/1:
- **Route guards use `beforeLoad` + `redirect`, never `<Navigate>` in a layout render.** The installed TanStack Router resolved to 1.170 (retail pins 1.57); its `Navigate` re-fires on every render while a redirect is pending and looped on logout. Keep this pattern for every new route.
- `frontend/src/routeTree.gen.ts` is generated by the router plugin during `vite build` / `vite dev`; it is committed so `tsc` works, never hand-edited.
- `debounce` in `lib/utils.ts` was changed to `ReturnType<typeof setTimeout>` (no `@types/node` here — though `@types/node` was later added as a *dev* dependency for the node-env pricing/fixture tests; `lib/utils.ts` itself is untouched).
- Migrations must stay idempotent; `migrations_idempotent_contract_test.go` enforces the accepted forms (`IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS` before `ADD CONSTRAINT`, `ON CONFLICT` on seeds).
- The isolation grep for the forbidden tenant name legitimately hits `CLAUDE.md` and `.claude/settings.json`, which name what to avoid; anywhere else is a violation. `docs/superpowers/` is also excluded from the grep gate (it can legitimately narrate the isolation rule while writing about it).
- JWT `iat` is whole-second, so a token minted in the same second as a revocation is rejected — tests look 2 s back.
- `settings.Save` casts `$2::jsonb` because lib/pq sends `[]byte` as bytea.
- `PUT /admin/settings` is all-or-nothing: one bad key fails the whole request, nothing partially saved.
- The raw-error contract test (`no_raw_error_contract_test.go`) is a same-line textual scan, not a full parse — keep `err.Error()` and the response line apart if either must appear near each other.
- `.superpowers/` is git-ignored scratch for the SDD ledger (task briefs, reports); nothing under it is part of the shipped repo.

From the demo path (D1–D10):
- **Admin day-ops routes live under `/admin/day/*`**, not `/day/*` as the original brief drafted — `routes.go` defines exactly two gated groups (`staff`, `admin`) and the contract test allows only those.
- **`net_sales`** on a closed `business_days` row is **Σ `total_payable`** (the rounded rupee figure the customer actually paid), not Σ `total_amount`. If a future reports task defines "net" differently, either change `dayops.Close`/`ForceClose` to agree or accept the daily report and the Z-report will disagree by a few rupees a day.
- **Invoice and receipt numbers accept gaps.** The number is allocated before the day gate and the credit-limit check run, so a refused sale burns a number (`R-…-002` after a refused attempt is expected, not a bug). Numbers stay unique and well-formed either way, which is what FBR rule 0173 needs.
- **`rounding_adjustment`'s achievable range is −0.49 … +0.50**, not "−0.50 … +0.49" as the spec's DB comment originally read (fixed in this task). Half-up ties round up; the algorithm can never land on −0.50 or +0.49.
- **Rate changes are logged only through `PUT /admin/rates`** — `PUT /admin/products/:id` has no rate field at all, by design, so every rate change writes `product_rate_history`.
- **A customer's `credit_limit` cannot be nulled back to "no limit"** through `PUT /admin/customers/:id` in v1 (every field is a plain pointer; nil means "leave unchanged", so there's no way to distinguish "clear it" from "don't touch it"). Set it to `0` instead until a tri-state field is added.
- **`formatDate` round-trips a bare `DATE` through `new Date()`**, which is off-by-one in negative-offset timezones. Not fixed in the demo path — **resolved in the Phase 5 polish sweep (P6)**: `CustomerDetail`'s statement now uses the existing `formatBusinessDate` (`lib/print/format.ts`) instead of a local re-implementation, and every date preset (invoices, reports) now computes "today" via `businessDateKey`, pinned to Asia/Karachi with `Intl.DateTimeFormat`, rather than the browser's own clock/zone.
- **Printing has not touched a physical printer.** The `@page` height lock, the 58 mm font scale and the VOID stamp opacity are reasoned from the retail POS's behaviour on 80 mm heads, not observed on this store's device. Print one of each (receipt, A4, Z-report) on the real printer before the demo. Still true as of the Phase 5 polish sweep — nothing has changed the print path's physical-hardware status.
- **The A4 invoice's buyer address was blank** unless a caller passed the `Customer` explicitly as `buildInvoiceA4Html`'s third argument. **Resolved in the Phase 5 polish sweep (P6)**: `printInvoice` now fetches the customer itself (`apiClient.getCustomer`) whenever the invoice carries a `customer_id` and passes `{address, province, buyer_registration_type}` through, so every caller (till, invoices drawer, recent-invoices strip) prints the full buyer block with no change on their end.
- **Counter staff can open, move cash and close the day without a PIN** (spec §3, as built) — Reopen and Force-close are admin-only and PIN-gated, but the everyday open/movement/close flow is not. This has not been re-confirmed with the owner during the demo path; see Owner questions below.
- **A known leftover row from D2's live smoke test**: an inactive product `Smoke Test Product __DELETE_ME__` (id `c93935c0-b7c3-437c-bb4d-1d6d618eea40`) is still sitting in the local dev database. It is inactive (`is_active=false`) so it does not appear on `/rates` (active-only) or in a fresh `GET /products?active=1`, but it does appear in the unfiltered product list. Left in place this task (deleting data outside this task's assigned scope needs the owner's or a dedicated task's sign-off per CLAUDE.md's destructive-SQL rule); safe to hard-delete with `DELETE FROM product_rate_history WHERE product_id = 'c93935c0-b7c3-437c-bb4d-1d6d618eea40'; DELETE FROM products WHERE id = 'c93935c0-b7c3-437c-bb4d-1d6d618eea40';` whenever convenient.
- **Exact-integer pricing.** Both languages resolve every intermediate money value to a scaled integer (paisa / micro-rupee) before any division, specifically to avoid float64 multiplication landing one ULP off an exact `.xx5` tie — see `backend/internal/pricing/pricing.go`'s doc comment for the worked example. Don't "simplify" this back to a float formula later without re-reading that comment.
- **Discount pro-rata uses the largest-remainder method** (Hamilton's apportionment), not "floor every line but the last and give the last the remainder" — the naive version can drive a small last line's discount above its own line total (negative taxable). Every line is capped at its own `line_total`.
